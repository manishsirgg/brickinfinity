# Owner-only listing and verification rollout

Only actual property owners, builders whose company owns the project, and BrickInfinity staff admins may list. Agents, brokers, marketing representatives and contractors without ownership are not eligible. Documents require human review; these controls cannot establish legal title automatically.

## Deploying

Apply earlier repository migrations first, including rental costs/availability and the description policy. Then run the **entire** `supabase/migrations/20261111_owner_only_verification.sql` file as the database owner in Supabase SQL Editor. It runs in a transaction and can be rerun. Deploy the accompanying application changes together with this migration. Back up and preview against a staging copy first.

After that migration, apply `supabase/migrations/20261111_owner_review_trigger_compatibility.sql`. It fixes `relation "documents" does not exist` when older triggers use unqualified public table names during a review. It changes function search paths and removes schema creation rights from ordinary API users; it does not change review decisions, publish properties or pause additional inventory. Keep `public` a trusted schema, with built-ins first and temporary objects last. Legacy functions that explicitly set their own incorrect search path still require a separate function-specific repair after inspecting their database definition.

Apply `supabase/migrations/20261111_declaration_seller_access.sql` after both migrations above. It preserves an already-active seller's access across owner/builder category changes when current approved government ID and selfie files remain valid. Existing property ownership decisions still reset for review. It does not bulk-activate existing accounts. To repair an account already stuck at inactive status, a staff admin opens Admin → Users, records a seller activation review note and selects **Activate Seller Access**. The database checks the declaration, approved identity documents and actual files, then updates both seller role and active status atomically. Inactive/demoted accounts cannot restore themselves merely by resaving a declaration; exceptions require the checked staff action. No property is automatically republished.

Next apply `supabase/migrations/20261111_reviewed_declaration_changes.sql` **before deploying this app version**. Installations with the three migrations above already applied can continue from this step. It replaces unrestricted post-verification changes with the reviewed request workflow below. It locks already-verified accounts, creates a private `declaration-documents` bucket, retains review evidence and leaves existing categories, activation states and published inventory unchanged. A migration guard rolls back if a legacy profile trigger unexpectedly changes account access or listing review state during locking; inspect those triggers before retrying. Do not reapply older function definitions after the newest migration; follow the order above.

Copy the entire newest file into a fresh SQL Editor query and run it together. It is one atomic `DO $reviewed_declaration_migration$ …` statement, with local JSON snapshots rather than session-scoped temporary tables. If an earlier attempt reported `brick_declaration_access_before does not exist`, rerun this corrected complete file; existing declaration columns, requests, decisions and evidence are preserved. Do not create that snapshot table manually or execute a schema-context export as a migration.

The original owner-only migration deliberately pauses existing non-admin published listings without the new ownership review. It also pauses published listings with legacy nonzero brokerage, including admin listings. Owners must record their declaration, complete their ownership fields and submit evidence for re-review. Existing approved identity evidence can be reused only when the actual stored files exist. Do not automatically republish legacy listings or manufacture review timestamps. Admin listings receive a separate source label, without automatic ownership or identity badges.

## Review workflow

1. The user records actual-owner or project-owning-builder capacity and accepts the no-agent declaration on Profile. Public admin-upgrade applications are removed.
2. Admins review one user application at a time in the KYC queue, with the latest government ID and matching selfie shown together. The on-page review note is used for each document's approval or rejection and is retained between decisions and after errors. Each pending document has its own decision/status; identity and seller activation are recomputed server-side after each decision and require the complete evidence set and declaration. Files must exist in private storage. Profile shows all three mandatory requirements and their current states; completing only one or two does not activate seller access.
3. Seller add/edit forms use the saved Profile owner category automatically, displaying it read-only with a Profile correction link. Personal legal names prefill from approved KYC; builder company names can reuse the account's previously approved ownership evidence. A personal KYC name is never guessed to be a company name. Existing listing legal names are retained unless the category changes; legal-name corrections require confirmation and ownership re-review. Builders enter the specific owned project for each listing. Property-specific ownership confirmation is required for new listings and ownership/location changes, but routine edits preserve it. Upload ownership evidence identifying the exact property/project and legal owner. Builders must show company ownership of the project; a brochure or marketing authorization is insufficient. Admins can enter owner details for their administrative listings.
4. The Ownership queue presents the identity/property evidence bundle with expiring signed links. Admins check identity match, property match, actual ownership and absence of an agent; builders additionally require company/project ownership. A review note is mandatory. Approval records the evidence paths, checklist, owner metadata, reviewer and timestamp.
5. An admin publishes after the ownership review. Staff-created listings follow a separate administrative path. Each public badge names the actual review performed; none guarantees clear legal title.

The Ownership page is a pending-review queue, not a list of all historical ownership documents. It includes only pending documents for non-deleted, pending properties with unreviewed/unverified ownership. Each property appears once using its latest pending evidence; supporting files remain accessible in the evidence bundle and audit. Confirmed approval/rejection removes the property from the pending list and closes its selected panel. The queue refreshes when returning to the tab/page and ignores older in-flight responses, so a property published or reviewed in another tab does not remain selected. New submissions or required ownership re-review can return it to the queue. No reviewed evidence is deleted by this UI refresh.

Material text/price/media changes return a listing to editorial review. Ownership/location changes also invalidate the ownership decision and reopen proof review. Availability reconfirmation and cover reordering alone do not require a new review. Revoking identity/seller access withdraws non-admin listings and clears their badges. Only an existing staff admin can grant/revoke staff access through the checked RPC; self-removal and removal of the last admin are blocked.

The admin Ownership audit page provides read-only ownership, account-security and listing-transition history. Evidence buckets are private; owners cannot overwrite/delete referenced reviewed evidence. Protect this retained personal data under the site's retention policy. Administrative deletion requires a separate controlled retention process.

## Changing a declaration after verification

- Before identity verification, applicants edit their category and declaration directly on Profile. After verification, a sticky server-side lock requires review for changes, even if the user subsequently resubmits KYC or loses seller access. A first declaration after approved KYC is still allowed when none was previously recorded.
- Profile shows the effective category. The user requests the other permitted category, provides its legal owner/company name, a reason of 10–2000 characters, the no-agent acceptance and 1–5 private PDF/JPG/PNG files up to 10 MB each. Only one pending request per account is allowed. Pending requests do not change the category, property visibility or account access.
- Users can cancel a pending request and see recent decisions and review notes. Cancellation/rejection preserves the effective declaration and retains the evidence/audit record. Referenced files cannot be replaced/deleted by API users; orphan uploads may be removed, but referenced evidence requires the controlled retention process.
- Admin → Declaration changes displays requests, private supporting files and the current government ID/selfie. Approval requires current approved identity files, a matching effective source category, all review checks and a note. Rejection requires a note but does not require a completed approval checklist. Stale, cancelled or already-decided requests cannot be approved. Admins cannot approve their own requests.
- Approval atomically updates the effective category and reviewed legal name, records the reviewer/checklist/note/current identity evidence, and reopens affected property ownership reviews. It preserves the existing role, KYC and seller activation flags, including inactive/demoted states. A new category cannot lift a suspension, restore rejected KYC or republish listings. Owning-company names approved here are available to property-form prefilling.
- Eligible active sellers retain their dashboard throughout a pending category request. Previously verified users with a saved declaration who are in the normal `pending` KYC / `pending_seller` re-review state can use `/seller-review`, a read-only page showing only their own listing statuses. Their normal dashboard routes redirect there; editing, publishing, promotions and CRM remain restricted. Rejected KYC and other inactive/suspended states do not gain this route. Account recovery still requires the checked Admin Users activation flow.

Request creation, cancellation and decisions are recorded in account-security history. The migration is repeatable and does not bulk-approve requests or automatically reactivate accounts.

## Legacy verification trigger conflict (11 November diagnostic)

After all migrations above, apply **`supabase/migrations/20261111_retire_legacy_verification_sync.sql`** in full as the database owner. This is one atomic, repeatable `DO` statement; it uses no temporary tables. A lock timeout or unexpected trigger binding rolls the statement back. Existing installations already up to date through reviewed declarations need only this new migration.

The production diagnostic identified three older bindings: `documents.sync_property_ownership_trigger`, `documents.sync_user_verification_trigger`, and `users.on_kyc_status_update`. Their legacy functions duplicate the checked review workflows and can overwrite `active` with obsolete `verified`, causing the canonical account guard to reopen ownership evidence during its own approval. The result is an approved property review paired with a pending document and inaccessible seller dashboard.

The migration checks each binding's exact public function name before retiring it, saves its original trigger definition in a private table, and retains the function itself. Identity/ownership guards, account invalidation, evidence retention, declaration locks, audit, SEO, pricing and notification triggers remain enabled. Future registrations use the existing checked ID/selfie/declaration workflow; property reviews no longer invoke the legacy account synchronization.

Recovery is deliberately limited. An account currently at `seller / approved / verified` is restored to `active` only with an existing explicit staff activation event, current identity files/declaration, and no later unexplained permission change. Every later permission change must match the timestamp and reviewer of an approved ownership review. Revoked/demoted accounts, other inactive statuses and accounts lacking this audit evidence are untouched and require explicit staff review. Each restoration is audited.

A pending ownership document is restored only when its current file, property owner metadata, full approval checklist and approval timestamp match an existing immutable approved ownership review, and current seller/identity eligibility and files remain valid. The original reviewer/timestamp are reused; genuine resubmissions remain pending. Each reconciliation is audited. **No listing is automatically published**: after the migration, open Admin → Listings and use Publish Now for a pending listing whose ownership review is complete. A fresh property review requires the normal checklist and note.

`supabase/diagnostics/ownership-review-reset.sql` is a read-only diagnostic for the reported property. It returns status, trigger and audit metadata without contact information or document paths. The migration does not run this diagnostic or depend on a hard-coded property/user ID. The PostgreSQL validation reproduces the deployed conflict, checks narrowly audited repairs, excludes unreviewed and subsequently demoted users, preserves true resubmissions and verifies future onboarding/publication.

## Resubmitting rejected property details

Apply `supabase/migrations/20261111_resubmitted_property_reviews.sql` after the owner-only, compatibility and legacy-trigger retirement migrations. A substantive property edit after ownership rejection reopens the retained rejected ownership evidence for a new human review. The property becomes pending/unreviewed, old rejection text is cleared from the current submission, and immutable decisions/notes remain in the audit. No-op saves and availability-only confirmations do not resubmit rejected listings. Rejected editorial listings with valid approved ownership return directly to publication review when substantively edited.

The migration also repairs non-deleted listings already stuck at pending with rejected ownership and matching retained rejected evidence. It requeues retained reviewed evidence for pending/unreviewed listings left without any pending document by older ownership/location edits. Unchanged rejected listings and listings without matching evidence are untouched. No ownership is approved, no listing published and no account activated by this migration. It is repeatable. If evidence itself was deficient, the seller should still upload corrected documents; reopening evidence does not make it acceptable or grant any verification badge.

Admin Console counts all non-deleted pending properties separately from those ready for publication. Ownership counts properties with actual pending ownership evidence, not supporting-file totals. Open Ownership Documents for evidence reviews and Listings for publication reviews. Count failures display an error rather than a false zero; returning to the browser tab refreshes the totals. Run `node scripts/validate-admin-dashboard-stats.mjs` and both owner-only database schema variants to verify this workflow.

## Explicit rejection and resubmission workflow

Apply `supabase/migrations/20261111_review_submission_workflow.sql` **after** the resubmission repair above and **before** deploying this app version. This new workflow supersedes automatic requeueing of edited rejected listings: an outstanding correction request keeps the property rejected during draft saves, document uploads and media edits. Existing pending submissions stay pending. Existing rejected properties receive imported correction records using their saved reason; the system does not guess whether their old reason specifically required new documents, and does not send fresh rejection notifications for imported decisions.

Admins reject through Ownership Documents or Listings using a reason, correction category (details, new ownership documents, or both) and specific required seller action. The checked rejection RPC locks the submission, validates that it still belongs to the queue, records the decision/correction request, and creates an in-site seller notification atomically. A failed notification rolls back the rejection. The old ownership-review rejection call is blocked; ownership approvals continue through the checked review RPC. Staff publication remains separate.

My Listings and Edit Property show the current reason and required action. Edit Property includes private rejection/resubmission history, **Save corrections as draft**, and **Resubmit for review**. Resubmit saves current form changes and calls the checked submission RPC. The server requires actual detail/media changes where requested, and a new pending document referencing a genuinely new stored file uploaded after rejection where new evidence is requested. Reusing the previously rejected file does not satisfy that requirement. New documents alone do not satisfy a details-and-documents correction request.

The submit RPC checks current seller/identity/owner details, ownership of the property, current rejection and evidence; locks the request/property; prevents duplicate submission; clears the active rejection only after the checks; and routes to ownership review whenever ownership is no longer approved. Editorial corrections retaining valid ownership go to listing publication review. Draft correction properties cannot receive ownership approval or publication. Resubmission creates an in-site confirmation and account audit event. Ownership approval creates a notification explaining that publication is a separate review. Publication retains its existing notification path. No email/SMS delivery is added here.

Correction requests and evidence remain private to their seller and staff; ordinary API clients cannot modify or delete the history or change submission-control flags directly. Earlier ownership decisions remain in the immutable audit. The migration is repeatable and does not approve, publish or reactivate accounts. Do not reapply superseded older trigger/function definitions after this migration.

Validation: both `node scripts/validate-owner-only.mjs` schema variants exercise structured rejection, private history, notification rollback, draft saves/uploads, required-correction checks, old-file reuse rejection, access checks, duplicate submission and ownership/publication routing. `node scripts/validate-property-review-ui.mjs` verifies instructions, correction categories, escaped text, history and separate save/submit actions.
